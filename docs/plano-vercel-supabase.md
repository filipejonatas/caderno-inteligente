# Plano de implementação — Vercel + Supabase

## 1. Objetivo

Preparar o Caderno Inteligente para ser publicado com:

- frontend React/Vite em um projeto Vercel;
- backend FastAPI em outro projeto Vercel;
- PostgreSQL do Supabase para casos, histórico, feedbacks e execuções;
- desenvolvimento local preservado, com SQLite como fallback quando `DATABASE_URL` não estiver configurada.

O objetivo é publicar um protótipo de hackathon com o mínimo de mudança na lógica de negócio. Cálculo de indicadores, score, leitura do Excel e contratos HTTP devem permanecer compatíveis.

## 2. Arquitetura-alvo

```text
Navegador
  │
  ├── Vercel: frontend Vite
  │       └── VITE_API_URL
  │
  └── Vercel: FastAPI
          ├── Excel e configurações empacotados no deploy
          ├── Pandas e regras atuais
          └── DATABASE_URL → Supabase Transaction Pooler
                                  ├── cases
                                  ├── case_history
                                  ├── feedback
                                  └── runs
```

Serão usados dois projetos Vercel ligados ao mesmo repositório:

1. `caderno-inteligente-api`, com raiz no repositório;
2. `caderno-inteligente`, com Root Directory em `frontend`.

## 3. Decisões de implementação

### 3.1 Manter SQLite no desenvolvimento local

Quando `DATABASE_URL` não existir, o backend continuará usando os arquivos em `runtime/`. Isso evita exigir Supabase para executar testes ou desenvolver localmente.

Quando `DATABASE_URL` existir, o backend usará exclusivamente PostgreSQL. Não haverá escrita simultânea nos dois bancos.

### 3.2 Acesso ao Supabase somente pelo backend

O frontend não receberá senha, service role key ou URL PostgreSQL. A única variável exposta ao Vite será a URL pública da API.

### 3.3 Conexão adequada a ambiente serverless

Usar a connection string **Transaction Pooler**, porta `6543`, com SSL. O código deve desabilitar prepared statements ao usar `psycopg` com transaction pooling.

Para o protótipo, cada operação pode abrir uma conexão curta por meio de uma fábrica centralizada. Pool persistente só deve ser adicionado depois de medir necessidade e comportamento em Functions congeladas.

### 3.4 Começar com banco vazio

Os arquivos `runtime/*.db` são artefatos locais ignorados pelo Git. A primeira publicação criará tabelas vazias no Supabase. Um importador dos dados SQLite existentes será opcional e ficará fora do MVP, a menos que a equipe confirme que esses registros precisam ser preservados.

## 4. Etapas de implementação

## Etapa 1 — Compatibilidade do runtime

### Arquivos

- `pyproject.toml`
- `.python-version` — novo
- `requirements.txt`
- `requirements-dev.txt` — novo, se a separação for viável

### Mudanças

1. Restringir o Python para evitar o problema já observado no 3.14:

   ```toml
   requires-python = ">=3.11,<3.14"
   ```

2. Criar `.python-version` com:

   ```text
   3.12
   ```

3. Adicionar o driver:

   ```text
   psycopg[binary]>=3.2,<4
   ```

4. Auditar as dependências de produção. Se os testes confirmarem que não são necessárias no backend publicado, mover `pytest`, `streamlit` e dependências exclusivas de desenvolvimento para `requirements-dev.txt`.

5. Declarar o entrypoint da Vercel:

   ```toml
   [tool.vercel]
   entrypoint = "backend.main:app"
   ```

### Critério de aceite

- ambiente novo criado com Python 3.12 instala todas as dependências;
- importação de `backend.main:app` funciona;
- testes locais continuam executáveis.

## Etapa 2 — Migration do Supabase

### Arquivos

- `supabase/migrations/001_initial.sql` — novo

### Tabelas

#### `cases`

- `id bigint generated by default as identity primary key`
- `sku text not null`
- `run_id bigint null`
- `status text not null`
- `owner text not null default ''`
- `due_date text not null default ''`
- `action text not null default ''`
- `note text not null default ''`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

#### `case_history`

- `id bigint generated by default as identity primary key`
- `case_id bigint not null references cases(id) on delete cascade`
- mesmos campos mutáveis do caso;
- `changed_at timestamptz not null default now()`

#### `feedback`

- `id bigint generated by default as identity primary key`
- `sku text not null`
- `action text not null`
- `note text not null default ''`
- `user_name text not null default ''`
- `partner_data_effect text not null default 'nao_utilizado'`
- `analysis_minutes integer null check (analysis_minutes >= 0)`
- `created_at timestamptz not null default now()`

#### `runs`

- `id bigint generated by default as identity primary key`
- `created_at timestamptz not null default now()`
- `source_hash text not null`
- `weights jsonb not null`
- `thresholds jsonb not null`
- `quality jsonb not null`
- `ranking jsonb not null`

### Regras adicionais

- adicionar índices para `cases(updated_at desc)`, `case_history(case_id, id desc)`, `feedback(id desc)` e `runs(id desc)`;
- adicionar checks para os valores aceitos de `status`, `action` e `partner_data_effect`, alinhados às constantes Python;
- habilitar RLS nas quatro tabelas;
- não criar políticas para `anon` ou `authenticated` nesta etapa, pois o acesso será feito somente pelo backend com a conexão PostgreSQL;
- tornar a migration idempotente onde for seguro, sem ocultar incompatibilidades de schema.

### Critério de aceite

- migration executa em um projeto Supabase vazio;
- segunda execução controlada não destrói dados;
- tabelas não ficam acessíveis anonimamente pela Data API;
- inserts e selects funcionam pela connection string do backend.

## Etapa 3 — Camada de persistência

### Arquivos sugeridos

- `src/caderno_inteligente/persistence.py` — novo
- `src/caderno_inteligente/postgres_persistence.py` — novo
- módulos SQLite existentes preservados inicialmente:
  - `cases.py`
  - `feedback.py`
  - `runs.py`

### Implementação

1. Definir uma interface ou protocolo com as operações usadas pela API:

   - listar, criar e atualizar casos;
   - consultar histórico do caso;
   - listar e criar feedback;
   - calcular resumo dos feedbacks;
   - listar, criar e buscar execuções.

2. Criar `SqlitePersistence`, delegando às funções atuais. Não duplicar a lógica SQLite.

3. Criar `PostgresPersistence` usando `psycopg`:

   - connection string recebida por construtor;
   - SSL definido pela connection string;
   - prepared statements desabilitados para o transaction pooler;
   - transações explícitas nas operações compostas;
   - `create_case` deve inserir `cases` e `case_history` na mesma transação;
   - `update_case` deve atualizar o caso e registrar o histórico na mesma transação;
   - timestamps devolvidos à API em ISO 8601;
   - campos `jsonb` devolvidos como objetos Python, sem dupla serialização.

4. Criar uma fábrica:

   ```text
   DATABASE_URL definida → PostgresPersistence
   DATABASE_URL ausente  → SqlitePersistence
   ```

5. Nunca registrar a connection string ou senha em logs e mensagens de erro.

### Critério de aceite

- endpoints mantêm os mesmos formatos JSON;
- falha em uma parte de uma operação composta não deixa dados parciais;
- testes SQLite atuais permanecem passando;
- testes unitários do adaptador PostgreSQL cobrem comandos, transações e conversões importantes.

## Etapa 4 — Integrar a persistência ao FastAPI

### Arquivo

- `backend/main.py`

### Mudanças

1. Remover o acoplamento direto dos endpoints aos caminhos:

   - `FEEDBACK_DB`
   - `CASES_DB`
   - `RUNS_DB`

2. Inicializar a persistência uma vez no módulo ou no lifespan da aplicação.

3. Trocar chamadas diretas de `create_case`, `list_feedback`, `create_run` etc. pelos métodos da camada de persistência.

4. Preservar rotas, status codes e payloads atuais.

5. Melhorar `/api/health` para informar, sem revelar credenciais:

   ```json
   {
     "status": "ok",
     "source_available": true,
     "database": "ok",
     "persistence": "postgres"
   }
   ```

6. Se a conexão ao banco falhar, o health check deve indicar indisponibilidade e os endpoints dependentes devem retornar erro controlado, sem stack trace ou connection string.

### Critério de aceite

- todos os endpoints atuais continuam respondendo com o banco local;
- os endpoints de leitura e escrita funcionam com `DATABASE_URL` de teste;
- o pipeline de indicadores continua independente do Supabase;
- score e ranking não sofrem alterações.

### Arquivos sugeridos

- `vercel.json` — novo, somente se necessário para limites ou inclusão explícita de arquivos
- `.vercelignore` — novo
- `.env.example` — novo na raiz

### Mudanças

1. Garantir que o bundle do backend inclua:

   - `backend/`;
   - `src/caderno_inteligente/`;
   - `config/`;
   - `data/source/Base de Dados - Caderno Inteligente.xlsm`.

2. Excluir artefatos que aumentam o bundle e não são necessários em runtime:

4. Confirmar que o backend não tenta escrever no diretório do projeto durante requests.

5. Documentar variáveis do projeto backend:

   ```text

   ```

### Critério de aceite

- deploy do backend fica abaixo do limite de bundle;
- `/api/health` responde na URL pública;
- arquivo Excel e configurações são encontrados em runtime;
- nenhuma escrita depende do filesystem da Function.

## Etapa 7 — Testes

### Testes automatizados

1. Executar toda a suíte Python com SQLite.
2. Adicionar testes da fábrica de persistência:

   - sem `DATABASE_URL` seleciona SQLite;
   - com `DATABASE_URL` seleciona PostgreSQL;
   - segredo nunca aparece em representação ou erro.

3. Adicionar testes de contrato do adaptador PostgreSQL para:

   - criar/listar/atualizar caso e histórico;
   - criar/listar/resumir feedback;
   - criar/listar/detalhar run;
   - rollback quando a segunda operação de uma transação falha.

4. Se não houver PostgreSQL descartável no CI, testar o SQL com mocks somente como primeira camada e executar uma validação manual obrigatória no Supabase de desenvolvimento.

5. Executar no frontend:

   ```text
   npm run check
   ```

### Testes manuais publicados

1. Abrir `/api/health`.
2. Carregar Visão geral, Prioridades, Qualidade e B2B2C.
3. Abrir detalhe de um SKU.
4. Executar uma simulação.
5. Criar um caso.
6. Atualizar o caso e conferir o histórico.
7. Registrar uma decisão.
8. Registrar uma execução.
9. Fazer novo deploy do backend.
10. Confirmar que casos, feedbacks e runs continuam presentes.
11. Conferir logs da Vercel e console do navegador.

## Etapa 8 — Publicação

### Supabase

1. Criar projeto na região mais próxima disponível.
2. Gerar uma senha forte e guardá-la fora do repositório.
3. Executar `001_initial.sql`.
4. Copiar a URL de **Transaction Pooler**, não a conexão direta.
5. Confirmar RLS e ausência de políticas públicas.

### Vercel — backend

1. Importar o repositório.
2. Usar a raiz do repositório como Root Directory.
3. Confirmar detecção do FastAPI por meio do entrypoint do `pyproject.toml`.
4. Cadastrar `DATABASE_URL`, `LOG_LEVEL` e temporariamente o domínio local ou futuro em `CORS_ORIGINS`.
5. Publicar e validar `/api/health`.

### Vercel — frontend

1. Importar o mesmo repositório em outro projeto.
2. Definir Root Directory como `frontend`.
3. Confirmar framework Vite, build `npm run build` e saída `dist`.
4. Definir `VITE_API_URL` com a URL pública do backend seguida de `/api`.
5. Publicar.
6. Atualizar `CORS_ORIGINS` do backend com a URL definitiva do frontend e republicar o backend.

## 5. Critérios de aceite gerais

- frontend e backend possuem URLs Vercel independentes e funcionais;
- nenhum segredo está presente no bundle do frontend, Git ou logs;
- backend utiliza PostgreSQL quando `DATABASE_URL` está configurada;
- ambiente local continua usando SQLite sem configuração extra;
- dados de casos, decisões e execuções sobrevivem a um redeploy;
- endpoints e formatos JSON existentes permanecem compatíveis;
- score, ranking, cenários e leitura do Excel permanecem inalterados;
- CORS aceita o frontend de produção e rejeita origens não configuradas;
- build frontend e testes Python passam;
- cold start inicial permanece dentro dos limites da Vercel;
- documentação de execução local e deploy está atualizada.

## 6. Segurança mínima para o protótipo

- nunca versionar `.env`;
- nunca usar `VITE_` em variáveis secretas;
- não expor senha do PostgreSQL, service role key ou `DATABASE_URL` ao navegador;
- habilitar RLS sem políticas públicas nas tabelas;
- limitar `CORS_ORIGINS` ao domínio oficial;
- não registrar payloads completos se futuramente contiverem dados sensíveis;
- lembrar que CORS não é autenticação: a API continuará pública nesta fase.

## 8. Riscos e mitigação

| Risco | Mitigação |
|---|---|
| Bundle Python grande | Separar dependências de desenvolvimento e excluir notebooks/artefatos |
| Cold start processando Excel | Manter cache por instância e medir antes de pré-calcular |
| Exaustão de conexões | Transaction Pooler, conexão curta e prepared statements desabilitados |
| CORS bloqueando o frontend | Publicar backend primeiro e atualizar a origem após obter a URL final |
| Divergência SQLite/PostgreSQL | Testes de contrato compartilhados entre os adaptadores |
| Escrita parcial | Usar uma transação para caso + histórico |
| Vazamento de segredo | Variáveis somente no backend e revisão do bundle/logs |
| API pública permitindo alterações | Usar apenas dados fictícios e planejar autenticação após o hackathon |

## 9. Estratégia de rollback

Se o adaptador PostgreSQL falhar durante a implementação:

1. não remover os módulos SQLite atuais;
2. executar localmente sem `DATABASE_URL`;
3. manter o último deploy funcional da Vercel disponível para rollback;
4. corrigir o adaptador sem alterar contratos da API;
5. não apontar produção para SQLite na Vercel, pois o filesystem não é persistente.

1. Etapa 1 — runtime e dependências.
2. Etapa 2 — migration SQL.
3. Etapa 3 — abstração e adaptadores de persistência.
4. Etapa 4 — integração FastAPI.
5. Etapa 5 — configuração do frontend.
6. Etapa 6 — arquivos da Vercel.
7. Etapa 7 — testes locais.

   - `DATABASE_URL` do Transaction Pooler;

   - URL do frontend após o primeiro deploy.
9. Etapa 8 — publicação e smoke test.

Estimativa para execução por IA: **3 a 5 horas**, sem contar criação de contas, confirmação de e-mail e esperas dos serviços externos.
